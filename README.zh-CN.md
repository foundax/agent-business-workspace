# 如何让你的内部业务 Agent 像 Codex / Claude Code 一样工作

> **核心理念：让模型用代码组织过程，让后端继续掌控规则与写入。**

[English](README.md) · [Quick Start](#4-快速上手quick-start) · 来自 [Foundax](https://foundax.com) 的工程参考项目

在复杂的企业级软件中接入 AI Agent 时，如果主要依靠大量离散业务工具组织任务，
跨模块的数据关联、操作组合与中间状态管理会变得越来越复杂。
本项目源于电商实战，旨在探索**如何将 Coding Agent（如 Claude Code、Codex）的工作范式引入已有复杂业务系统**。

**本仓库提供什么：**

- 一套将业务数据映射为“可探索代码与数据快照”的业务 Agent 参考架构。
- 包含合成数据、修改建议（Proposal）生成、宿主校验与执行的完整可运行示例。
- 关于代码快照、数据缓存与沙箱执行隔离的工程设计说明。

*(注：本项目是工程架构参考，并非可直接替换现有 Agent Harness 的开箱即用框架。)*

---

## 1. 为什么复杂业务 Agent 需要的不只是 Tool Calling？

Tool Calling 是模型调用外部能力的机制。Coding Agent 同样通过工具读取文件、执行代码，
并在持续的工作环境中保存脚本和中间结果。
这里讨论的是：当业务组合无法预先穷举时，如何组织业务上下文、操作组合与执行状态。

### 真实业务场景的挑战

已有业务系统通常具备成熟的数据模型、API、业务服务（Domain Service）和权限体系。但用户往往只提出一个**业务目标**。例如，在 [Foundax](https://foundax.com) 的电商场景中，商家会直接要求：

> “帮我准备周末活动：筛选库存充足的商品，补齐缺失的中英文介绍，设置合适的优惠，先让我确认改动。”

要完成这句话，Agent 必须在执行过程中动态理清：

- **“库存充足”**：需关联商品规格（Variants）并计算 `可售库存 = 现有库存 - 预留库存`。
- **“介绍缺失”**：需跨商品主表与多语言内容表进行比对。
- **“设置优惠”**：需校验促销适用范围与既有冲突规则。

### 离散业务工具的组织成本

一种常见做法是把后端能力逐一包装成工具（如 `get_products`、`check_inventory`、`update_content`）。
当业务上下文和执行状态主要通过这些工具的定义与返回值传递时，跨域任务会增加两类组织成本：

1. **业务关系碎片化**：商品、规格、库存的关联逻辑散落在多个接口文档里，甚至同一字段在读写接口中命名不一。
2. **组合爆炸与维护成本**：业务组合无法穷举，新增字段或查询维度时，往往需要同步维护多个 Tool Schema。工具检索（Tool Retrieval）能够减少一次加载的工具定义，但模型仍需发现合适的工具，并组合不同工具返回的数据与状态。

### 三种 Agent 组织方式的取舍

以下方式可以组合使用：工作流和代码执行都可以调用工具。
选择重点在于步骤由谁决定、业务关系如何呈现，以及中间状态如何保存。
关于工作流与动态决策的区别，可参考 Anthropic 的 [Building effective agents](https://www.anthropic.com/research/building-effective-agents)：

| 组织方式 | 循环推进机制 | 适用场景 | 局限性 |
| --- | --- | --- | --- |
| **预定义工作流 (Workflow)** | 程序固定步骤，模型仅负责局部判断或生成 | 路径稳定、验收标准明确的任务 | 新增任务路径通常需要调整流程定义 |
| **离散业务工具组合** | 模型选业务工具 -> 读结果 -> 决定下一次调用 | 已有接口能直接表达的任务（如查单） | 跨工具的数据关联与状态传递需要额外协调 |
| **代码执行与持续工作环境** | 模型读项目与数据 -> 写代码执行 -> 检查结果并迭代 | **动态探索、跨域关联、批量计算与连续修改** | 需承担执行隔离与会话存储的工程成本 |

**我们的选择是**：对于下一步取决于探索结果、需要灵活组合数据的复杂业务，
**让模型直接看到稳定的业务数据结构，用代码组织过程，并在持续的工作环境中保存中间状态**。
明确的业务操作仍通过工具或业务服务执行，已有工作流也可以承担其中路径稳定的步骤。

## 2. 核心架构：它是如何工作的？

Foundax 内部 Agent 已使用只读快照、隔离执行环境和宿主业务服务。
本节将这些实践抽象为**“只读快照探索 + 代码生成修改建议 + 宿主校验写入”**的参考架构。
本仓库的可运行实现聚焦合成数据读取、修改建议生成和内存业务服务校验；运行时与缓存机制通过工程设计文档说明。

```mermaid
flowchart LR
    Backend[业务数据与源码] --> Snapshot[1. 限定范围的只读快照]
    Snapshot --> Agent[2. Agent 读表结构/写代码计算]
    Agent --> Proposal[3. 生成结构化修改建议]
    Proposal --> Review[4. 宿主侧预览与授权]
    Review --> Service[5. 既有业务服务校验并写入]
    Service --> Readback[6. 读取更新后的业务视图]
```

### 设计支柱一：让表结构与业务含义成为可读取的上下文

我们不再为每个任务组合开发专用 Tool，而是向 Agent 暴露围绕核心业务对象组织的 Schema 视图与业务契约：

```text
products(id, name, ...)
variants(id, productId -> products.id, ...)
inventory(variantId -> variants.id, onHand, reserved)
product_content(productId -> products.id, locale, title, description)
```
*(注：以上为示意视图，非生产表结构。)*

- **按需渐进式探索**：入口仅提供目录与关系索引，不必将整个数据库或代码库塞进 Prompt。模型按需读取表定义、主键粒度、字段约束（如 `available = onHand - reserved`）及授权源码。
- **读写语义统一**：模型用同一套字段结构完成关联查询、筛选计算，并输出修改建议，减少跨工具的字段映射与语义转换。

### 设计支柱二：参考架构中的四类挂载与快照复用

参考架构将 Agent 编写的代码放在受控执行沙箱（Execution Sandbox）中，
通过四类逻辑挂载分别管理代码、数据、会话文件和交付产物：

| 挂载点 | 存放内容 | 生命周期与复用策略 |
| --- | --- | --- |
| `/repo` | 授权可读的源码、表定义、业务规则说明 | **版本化只读快照**：在相同授权的会话间直接共享，免去重复扫描 |
| `/data` | 当前租户/权限范围内的业务数据快照 | **按范围缓存**：按依赖刷新受影响的业务域，避免每轮全量查库 |
| `/work` | Agent 编写的脚本与中间计算结果 | **会话级独立**：在多轮连续任务中持久化保留，减少重复计算 |
| `/outputs` | 最终生成的修改建议（Proposal）与交付物 | **结构化产物**：由宿主应用读取、校验并进入审批流 |

**Demo 对应实现：**脚本、JSON 数据和修改建议保存在普通本地目录 `.demo/workspace` 中。
仓库未实现上述沙箱挂载、快照缓存或自动刷新；这些机制在工程文档中以设计与伪代码呈现。

> **工程深入阅读**：关于如何构建快照缓存键、处理缓存失效与沙箱隔离，详见 [《工程说明：快照缓存、缓存失效与执行隔离》](docs/workspace-lifecycle.zh-CN.md)（内含简化伪代码与生命周期设计）。
>
> **性能收益参考**：在内部执行器优化过程中，会话启动耗时从 **~2.1s 降至 1.0–1.4s**，首个工具链命令耗时从 **~0.87s 降至 0.10–0.15s**。
> 以上为工程参考值，具体取决于部署环境。本地计算与状态保持也有助于减少中间结果的重复传输。

### 设计支柱三：模型负责过程，后端握紧写入

- **Agent 侧决策**：诸如“盘点后若无可用库存则暂停商品”这类任务级逻辑，由 Agent 写在沙箱脚本中，最终仅产出一份声明式的**修改建议（Proposal）**。
- **宿主侧执行**：业务凭据、权限校验和最终落库始终留在宿主应用（Host Application）。宿主读取修改建议后，交由原有的**业务服务（Domain Service）**校验店铺范围、可写字段、预留库存及数据版本号（用于乐观并发控制），按已有事务边界执行。
- **外部副作用管控**：扣款、退款、发送通知等具有外部副作用的动作，依然通过具备明确语义和授权的业务命令处理。

这种契约让内部 Agent 与外部 Coding Agent 能够复用相同的数据结构与操作接口，减少业务能力对特定 Agent 编排的依赖。

## 3. 跨行业普适性：不止于电商

这套“暴露授权 Schema 与数据快照 -> 模型写代码跨域组合 -> 业务服务管控写入”的模式，可以迁移到其他复杂企业软件：

| 业务系统 | 典型用户目标 | Agent 通过代码关联探索的业务对象 |
| --- | --- | --- |
| **CRM** | 找出高价值且有流失风险的客户，生成挽回方案 | 客户档案、历史订单、沟通记录、客户分层规则 |
| **ERP** | 核算下月物料缺口，生成采购单调整建议 | 物料清单 (BOM)、实时库存、在途采购单、生产计划 |
| **财务系统** | 排查异常费用报销，生成调账或驳回建议 | 记账凭证、会计科目、关联合同、成本中心预算 |
| **营销平台** | 识别低 ROI 广告组，提出跨渠道预算调配方案 | 广告组、受众定向、转化归因数据、日预算上限 |
| **HR 系统** | 结合排班与请假审批，预测下周门店人力缺口 | 员工档案、岗位技能、排班表、休假记录、工时合规规则 |

## 4. 快速上手（Quick Start）

本仓库提供一个聚焦**“库存盘点核对”**的可运行示例（无需安装第三方依赖，无需配置大模型 API Key 或数据库，需 **Node.js 22+**）。

示例使用手写程序复现流程，不调用模型；前文的多语言内容与促销场景不包含在本 Demo 中。

### 第一步：体验完整的“提议 -> 校验 -> 执行”闭环

在仓库根目录下依次执行：

```sh
# 1. 运行盘点核对脚本，生成修改建议
npm run demo

# 2. 由宿主校验修改建议，并应用到内存业务数据中
npm run apply-demo
```

**背后发生了什么？**

1. `npm run demo` 会初始化 `.demo/workspace` 示例目录，运行参考脚本读取合成商品与盘点数据，计算出需要修正的库存，并将无可用库存的商品标记为暂停，最终生成修改建议文件 `.demo/workspace/output/changes.json`：
   ```json
   [
     { "id": "mug", "expectedRevision": 3, "set": { "onHand": 5 } },
     { "id": "vase", "expectedRevision": 7, "set": { "onHand": 1, "status": "paused" } }
   ]
   ```
2. `npm run apply-demo` 模拟宿主后端：读取该 JSON，校验店铺范围、可写字段约束及 `expectedRevision` 数据版本，校验通过后更新内存中的商品数据，并打印更新后的业务视图。

每次执行从同一份合成数据开始，更新后的状态仅保留在当前进程内。

### 第二步：接入你自己的 Coding Agent 试一试

你可以用自己日常使用的 Coding Agent（如 Claude Code、Codex、Cursor 等）替换掉手写的示例脚本：

```sh
# 1. 重置并准备干净的示例目录（注意：会覆盖已有的示例生成文件）
npm run prepare-demo

# 2. 让你的 Coding Agent 打开 .demo/workspace 目录
#    提示它阅读 WORKSPACE.md 和 TASK.md，重写 task.mjs
# 3. 人工检查 Agent 编写的 task.mjs 代码后，执行它以生成修改建议
npm run propose-demo

# 4. 宿主校验并执行 Agent 生成的建议
npm run apply-demo
```

### ⚠️ 本地 Demo 与生产环境的边界说明

- **本地并非真实沙箱**：本仓库的 Demo 脚本直接以当前操作系统的用户权限在独立 Node 进程中运行，可读取本地仓库文件。**生产环境需要独立的执行隔离**，并确保宿主环境不受 Agent 控制。
- **生产级事务与鉴权**：Demo 在内存中完成整批校验与状态更新。在生产系统集成时，需接入真实的宿主身份认证、针对单条/批次修改建议的审批流，以及业务服务层的数据库事务。
