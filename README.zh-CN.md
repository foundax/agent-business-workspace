# 让现有业务系统成为 Coding Agent 的工作环境

> **让模型用代码组织过程，让后端继续掌控规则与写入。**

[English](README.md) · [运行示例](#2-运行示例库存盘点核对) · 来自 [Foundax](https://foundax.com) 的工程实践

一家成熟的软件企业，已经拥有数据库、业务接口、领域服务和权限体系。
当它为 CRM、ERP、电商或营销系统接入 Agent 时，需要解决一个具体问题：
**怎样把这些现有资产组织成 Agent 可以理解、探索和操作的业务环境？**

本项目源于 Foundax 的电商业务实践，分享三个相互关联的工程问题：

- **业务如何被理解：**将授权数据、实体关系、字段含义与操作契约呈现为可读取的上下文。
- **数据变化后如何继续：**分别管理源码、业务快照和会话文件，通过依赖版本刷新数据。
- **修改如何进入真实系统：**模型生成修改建议，由宿主与既有业务服务校验并执行。

## 1. 从一个业务目标开始

商家可能提出这样的要求：

> 帮我准备周末活动：筛选库存充足的商品，补齐缺失的中英文介绍，设置合适的优惠，先让我确认改动。

Agent 需要理解“库存充足”的计算口径，关联商品、规格和多语言内容，并遵守促销规则。
任务期间，其他人还可能调整库存或修改商品。用户确认时的数据，未必仍是 Agent 生成建议时的数据。

| 业务问题 | 需要明确的工程契约 |
| --- | --- |
| 哪些商品属于当前任务？ | 用户选定范围与当前权限共同限定可读资源 |
| 一行库存代表商品还是规格？ | 行粒度、关联键、单位及 `available = onHand - reserved` 等计算口径 |
| 当前数据覆盖全部商品吗？ | 快照时间、筛选条件与完整性标记 |
| 其他人修改了库存怎么办？ | 数据刷新规则与最终写入时的版本冲突处理 |
| 模型能决定哪些事？ | 任务级筛选与计算由模型组织，长期业务约束由领域服务维护 |

这些问题也出现在 CRM 的客户与互动记录、ERP 的物料与采购计划、营销平台的广告与归因数据中。
项目分享的是对现有业务系统的接入方法，示例使用合成的商品与盘点数据。

### 实践来源与仓库交付范围

| 层次 | 内容 |
| --- | --- |
| Foundax 内部实践 | 授权业务视图、源码与数据快照、隔离执行、宿主业务服务写入 |
| 公开工程设计 | 数据契约、缓存复用、依赖失效、隔离边界与一致性要求，通过文档和伪代码说明 |
| 仓库可运行实现 | 本地 JSON 数据、盘点脚本、结构化修改建议、内存业务服务与测试 |

Demo 使用普通本地目录与 Node 进程，不包含模型调用、沙箱运行时、快照缓存或自动刷新实现。

## 2. 运行示例：库存盘点核对

需要 **Node.js 22+**。无需第三方依赖、模型 API Key 或数据库。在仓库根目录依次运行：

```sh
npm run demo
npm run apply-demo
```

`npm run demo` 准备 `.demo/workspace`，执行手写参考脚本，读取商品与盘点数据并生成修改建议：

```json
[
  { "id": "mug", "expectedRevision": 3, "set": { "onHand": 5 } },
  { "id": "vase", "expectedRevision": 7, "set": { "onHand": 1, "status": "paused" } }
]
```

建议保存在 `.demo/workspace/output/changes.json`。
`npm run apply-demo` 代表宿主执行阶段：读取建议，校验店铺范围、可写字段、预留库存与版本号，
校验通过后更新内存数据并打印结果。每次执行从同一份合成数据开始，更新仅保留在当前进程内。

这个示例聚焦盘点核对；上文的多语言内容与促销任务用于说明更大的业务背景。

### 在代码中检查业务边界

| 情况 | 示例行为 |
| --- | --- |
| 导出商品数据 | 仅返回当前店铺的业务字段，不包含成本字段 |
| 提交其他店铺的商品 ID | 拒绝修改 |
| 尝试修改 `reserved`、成本或店铺字段 | 拒绝修改 |
| 盘点库存低于已预留数量 | 拒绝修改，要求先处理库存差异 |
| `expectedRevision` 与当前版本不一致 | 拒绝旧建议，要求重新读取并生成建议 |
| 一批建议中存在无效修改 | 整批拒绝，保留原内存数据 |

对应实现：[业务服务](src/catalog-service.mjs)、[盘点脚本](examples/reconcile-stocktake.mjs)、
[数据契约](workspace/WORKSPACE.md)和[测试](test/workspace.test.mjs)。
这里的字段投影用于展示读取契约；本地进程仍拥有当前操作系统用户的文件访问权限。

### 使用自己的 Coding Agent

```sh
# 重置生成文件，会覆盖已有示例脚本与数据
npm run prepare-demo

# 用 Coding Agent 打开 .demo/workspace
# 让它阅读 WORKSPACE.md 和 TASK.md，编写 task.mjs
# 检查生成的代码后运行
npm run propose-demo

# 宿主校验并应用建议
npm run apply-demo
```

生产接入需要将示例中的固定店铺范围与内存更新，替换为真实身份授权和领域服务的数据库事务，
并在独立执行环境中运行模型生成的代码。

## 3. 把现有业务资产组织成可探索的环境

### 3.1 读取契约：从数据库结构到业务含义

原始 Schema 描述存储结构，Agent 还需要知道行的含义、关联路径、计算口径和允许的操作。
宿主先通过已有业务读取服务完成权限过滤与数据投影，再提供业务视图。例如：

```text
products(id, name, ...)
variants(id, productId -> products.id, ...)
inventory(variantId -> variants.id, onHand, reserved)
product_content(productId -> products.id, locale, title, description)
```

以上为示意视图。读取契约应同时说明：

- **实体与关系：**主键、外键、单行粒度及跨表关联方式。
- **字段语义：**类型、单位、枚举和派生值，例如可售库存的计算规则。
- **可见范围：**租户、用户权限、选定资源，以及部分导出的过滤条件。
- **修改边界：**哪些字段可以提出修改，哪些约束由后端执行。

入口先提供目录和关系索引，再按需读取目标表与源码。
任务筛选范围可以缩小授权视图；扩大筛选范围时，宿主仍需重新核验读取权限。
同一业务字段在读取视图和修改建议中使用一致命名，减少跨接口的语义映射。

### 3.2 数据生命周期：减少查库，同时保留任务状态

一次任务会反复筛选、关联和计算数据。把已授权的数据准备为 JSON 或本地 SQLite，
可以将已覆盖数据的探索查询移到执行环境中；首次导出、超范围补查与后续刷新仍由宿主完成。

源码、业务数据与会话文件有不同的变化来源。参考设计将它们分为四类逻辑挂载：

| 挂载点 | 内容 | 生命周期 |
| --- | --- | --- |
| `/repo` | 授权源码、表定义、业务契约 | 版本化只读产物，在相同源码可见性下共享 |
| `/data` | 当前权限范围内的业务数据 | 按授权范围缓存，按依赖刷新受影响的域 |
| `/work` | 脚本与中间计算结果 | 会话独立保存，刷新数据时保留 |
| `/outputs` | 修改建议与交付产物 | 交给宿主读取、校验和执行 |

例如，用户确认库存修正后，Agent 要继续准备活动，应先更新受影响的库存视图，
再使用保留的脚本继续计算。单次命令固定读取一个快照版本，新数据在命令之间切换。

[快照生命周期工程设计](docs/workspace-lifecycle.zh-CN.md)进一步说明缓存键、任务投影、
依赖水位、并发构建与一致性条件。上述挂载和缓存机制属于参考设计；Demo 使用第 2 节的普通本地目录。

### 3.3 写入契约：任务逻辑与业务约束分别维护

“筛选哪些商品”“盘点后是否暂停无可售库存的商品”属于任务逻辑，模型可以用代码组织。
店铺归属、可写字段、库存约束、数据版本和促销规则由业务服务维护。

```mermaid
flowchart LR
    Read[授权业务视图] --> Code[Agent 关联与计算]
    Code --> Proposal[结构化修改建议]
    Proposal --> Review[宿主预览与授权]
    Review --> Validate[业务服务校验当前状态]
    Validate --> Write[按领域事务执行]
    Write --> Result[返回实际结果与刷新需求]
```

宿主接收的是显式的业务变更，不是任意数据库写入权限。
`expectedRevision` 将建议绑定到它依据的数据版本；发生冲突时，重新读取相关数据并重新计算，
不能仅替换版本号后重试原建议。

代码计算完成、用户批准建议与业务写入成功是三个不同阶段。
对外展示结果应以业务服务的实际返回值为依据。跨域批量任务还需明确事务范围、部分成功和重试语义。
扣款、退款、发送通知等外部副作用继续通过有明确授权的业务命令执行。

## 4. 工程取舍与执行框架

业务接口能够直接表达的任务，可以直接调用工具；路径稳定的任务，可以由工作流组织。
需要动态关联多类对象、批量计算并保留中间结果时，代码执行与持续工作环境更便于组合已有能力。
这些方式可以共同使用，Coding Agent 同样通过 Tool Calling 读取文件与执行命令。

选择数据快照也意味着承担导出、存储、权限变化与数据新鲜度管理的成本。
快照适合探索与计算；最终写入仍需基于业务服务的当前状态进行校验。
具体成本与可观测性见[工程设计第 6 节](docs/workspace-lifecycle.zh-CN.md#6-性能收益拆解与可观测性)。

[OpenHands Software Agent SDK](https://docs.openhands.dev/sdk/arch/overview)提供执行循环、工具、会话与执行环境等通用组件。
本项目讨论接入既有业务系统时需要定义的数据与操作契约，供使用现有框架或自建运行时的团队参考。
当前示例通过本地脚本展示这些契约，没有提供特定 Agent SDK 的集成适配器。

## 5. 参与贡献与工程交流

我们希望围绕具体业务问题积累可以复用的设计与案例：

- **业务数据契约：**如何表达 CRM 客户关系、ERP 物料单位或营销归因口径，使 Agent 能正确关联与计算。
- **状态变化与冲突：**数据在探索、审批或续跑期间发生变化时，如何刷新、拒绝旧建议并保留有效工作。
- **领域服务接入：**如何复用已有权限、校验和事务边界，明确批量任务的部分成功与重试行为。
- **工程取舍：**使用合成案例说明快照粒度、查库负载、准备耗时与任务完成质量之间的关系。
