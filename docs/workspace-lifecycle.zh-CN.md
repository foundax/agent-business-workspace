# 工程设计说明：快照缓存、缓存失效与执行隔离

[English](workspace-lifecycle.md) · [返回项目介绍](../README.zh-CN.md)

具备代码执行能力的业务 Agent 在运行时需要同时访问三类状态：**源代码与业务契约**、
**授权范围内的业务数据**以及**会话级文件**。它们的生命周期设计直接影响存储增长、
生产数据库（OLTP）的查询负载、业务变更何时对 Agent 可见，以及长任务中断后的状态恢复。

本文将 Foundax 的工程实践整理为一套参考设计：使用**不可变源代码快照（Immutable Source Snapshot）**、
**限定范围的数据快照（Scoped Data Snapshot）**、**基于版本水位的缓存失效（Watermark-Based Invalidation）**
和**隔离执行沙箱（Execution Sandbox）**，通过挂载拓扑、缓存键与伪代码说明各层如何协作。

下文描述运行时与缓存的参考设计。本仓库的可运行示例实现合成数据读取、修改建议生成与内存业务服务校验，
使用普通本地目录运行，未实现文中的沙箱挂载、快照缓存与自动刷新。

## 1. 运行时拓扑与存储生命周期分层

### 1.1 宿主与沙箱的职责边界

系统分为**可信宿主应用（Trusted Host Application）**与**隔离执行沙箱（Isolated Execution Sandbox）**。
模型调用与任务编排、身份鉴权、快照准备及最终业务写入由宿主管理；模型生成的代码在沙箱内运行。

```text
可信宿主应用（Trusted Host Application）
  身份鉴权 / 模型编排 / 快照构建与缓存 / 修改建议审阅 / 业务服务写入
      │
      │  注入只读快照、下发执行指令、回收交付产物
      ▼
隔离执行沙箱（Shell / Node / SQLite）
  /repo     [只读] 版本化源代码、Schema、业务契约文档
  /data     [只读] 当前租户与权限范围内的数据快照（JSON / SQLite）
  /work     [读写] 会话脚本与中间计算状态
  /outputs  [读写] 结构化修改建议（Proposal）与交付产物
```

### 1.2 安全隔离与资源约束

1. **权限分离。** 源码读取、沙箱执行和业务写入分别授权。
   宿主接收修改建议后，按当前权限、业务规则与数据版本执行校验；代码执行权限不授予数据库写入权限。
2. **凭据与网络隔离。** 生产数据库凭据和内部服务密钥不进入沙箱的环境变量或文件系统。
   沙箱默认禁用外部网络访问；任务需要的外部能力通过宿主提供的授权代理访问。
3. **运行时隔离与配额。** 宿主管理物理路径，向 Agent 暴露固定的逻辑挂载路径。
   运行时提供进程、文件系统和网络隔离，并限制 CPU、内存、磁盘容量与 I/O。
   Linux Namespace、Cgroups、文件系统配额或 MicroVM 可承担不同层面的约束，部署时需分别配置。
4. **命令级快照一致性（Command-Scoped Snapshot Consistency）。**
   单次命令执行期间固定 `/data` 版本，完整的新快照只在命令之间切换。
   一种实现方式是停止旧沙箱，再以新快照启动沙箱，同时重新挂载原有的 `/work` 与 `/outputs`。
   文件状态得以保留，进程内存不会随之保留。宿主需向模型提供当前快照版本。

这里的一致性指命令读取固定的一组文件；数据库导出的事务一致性由第 4 节的数据准备协议保证。

### 1.3 状态分层与复用粒度

代码、数据和会话状态独立存储，分别维护版本与引用关系。

| 存储层 | 核心内容 | 变更触发源 | 复用粒度 |
| --- | --- | --- | --- |
| `/repo` | 授权源码、业务契约、领域文档 | 应用发布、契约或访问策略变更 | 构建版本 × 源码访问策略 |
| `/data` | 业务实体、关系与约束元数据 | 业务写入、权限或数据契约变化 | 租户 × 权限范围 × 业务域 |
| `/work`、`/outputs` | 脚本、中间结果、修改建议 | Agent 推进任务 | 会话或连续任务 |

同一源码访问策略下的会话可以共享代码产物。业务数据按租户和授权范围隔离；
会话文件独立保留，使任务能够在数据刷新后继续使用已有脚本和产物。

## 2. 不可变源代码快照（/repo）

源代码快照是一份版本确定、保留文件关联且支持本地检索的只读副本，
包含授权可见的业务源码、表结构定义、业务规则说明及操作契约。

### 2.1 四阶段构建与挂载流水线

1. **源码裁剪与策略过滤。** 依据源码访问策略（Source Access Policy）选择文件，
   排除密钥、环境文件（`.env`）、数据库转储、Git 历史及无关构建产物。
2. **文件清单与入口索引。** 清单（Manifest）记录相对路径、文件大小和内容摘要。
   入口索引列出业务域、表关联定义、字段约束和操作入口所在的文件，供模型按需检索。
3. **不可变产物封存。** 在构建或预热阶段完成文件访问策略与内容检查，生成不可变产物。
   执行节点导入时验证内容摘要，随后由宿主以只读方式管理。
4. **会话共享只读挂载。** 启动时按版本定位已导入的产物，将其挂载到 `/repo`，
   例如使用只读绑定挂载（Read-Only Bind Mount），无需为每个会话再次复制代码。
   发布新版本时创建独立产物，运行中的任务继续引用原版本。

### 2.2 缓存寻址模型与安全前提

```text
codeKey        = Hash(buildVersion, sourceAccessPolicyVersion, contractVersion)
artifactDigest = ContentDigest(manifest + fileContents)
session.repo   = ReadOnlyRef(artifactDigest)
```

**缓存寻址与鉴权分离。** `codeKey` 用于查找可复用版本，内容寻址摘要（Content-Addressed Digest）
`artifactDigest` 标识具体产物。会话挂载前仍需通过源码读取授权；只有允许读取同一份内容的会话才能共享引用。

**可信发布与不可变存储。** 构建和导入阶段完成内容检查后，会话可以复用已验证的产物，省去重复扫描。
前提是产物只能由可信发布流程写入，且导入后的内容保持不可变。

### 2.3 共享存储开销与垃圾回收

在同一执行节点或共享存储池内，多会话引用同一份只读代码产物。
代码层的容量随保留版本数增长，无需随会话数重复增长：

```text
代码层存储 ≈ 保留代码版本数 × 单份代码快照体积
总存储     ≈ 代码层存储 + 数据快照存储 + 会话文件存储
```

容量统计包含活跃状态和保留的历史状态。多个执行节点各自导入产物时，还需计入节点间的副本。
数据投影、脚本和输出的存储占用分别统计。

垃圾回收采用**引用追踪（Reference Tracking）与可达性判断（Reachability-Based GC）**：
以活跃会话、当前发布和回滚保留版本为根，保留其引用的产物；回收无引用且超出保留窗口的历史产物。

## 3. 授权数据快照与任务视图投影（/data）

宿主在当前用户的权限范围内，调用已有的领域读取服务（Domain Read Services）准备数据。
沙箱探索的是这些数据的本地只读副本。

```text
宿主授权读取 → 按业务域组织实体 → 附带关系与约束元数据
            → 物化为 JSON / 本地 SQLite → /data 只读视图
```

### 3.1 自包含的 Schema 元数据契约

数据快照附带表定义，使模型可以直接确定行的含义、关联路径和字段约束。

| 元数据维度 | 工程用途 |
| --- | --- |
| 行粒度、主键与外键 | 定义业务实体边界和跨表关联键（Join Keys） |
| 类型、单位、枚举与计算约束 | 支持筛选、聚合和前置校验，例如 `available = onHand - reserved` |
| 可写字段（Writable Fields） | 定义修改建议可涉及的字段，最终由宿主执行字段校验 |
| 授权范围、快照时间与完整性标记 | 说明数据的时间截面、过滤条件和覆盖范围 |

### 3.2 存储格式与读写语义

**统一业务字段命名。** 读取视图与修改建议中的同一业务字段使用相同名称，
减少读取用 `stock`、写入用 `target_stock` 带来的重复映射。

**JSON 与 SQLite 分工。** JSON 适合查看少量实体、读取配置和生成修改建议；
SQLite 适合多表关联（JOIN）、条件过滤及聚合。Agent 可以反复查询本地副本，将计算结果写入 `/work`，
把快照已覆盖数据的探索查询从生产库转移到沙箱。首次导出、补充查询和刷新仍由宿主完成。

**渐进式读取与部分导出。** 入口先提供表目录和关系索引，模型再按需读取具体表和行。
部分导出（Partial Export）应在元数据中记录筛选条件与覆盖范围，让模型区分当前结果集和完整业务数据。

### 3.3 二级复用：基础快照与任务投影

基础数据快照（Base Snapshot）按授权范围缓存；任务视图投影（Task Projection）
在其基础上应用用户选定的资源与过滤条件。

```text
dataKey   = Hash(tenantId, resourceScope, locale, authorizationFingerprint, dataContractVersion)
taskScope = Canonicalize(selectedResourceIds, explicitFilters)
```

- **基础快照键 `dataKey`。** `resourceScope` 标识店铺、部门或项目等业务边界；
  `authorizationFingerprint` 纳入影响行级和字段级可见性的授权条件，使不同权限视图使用不同缓存键。
- **任务范围 `taskScope`。** 对资源 ID 去重、排序，并规范化过滤条件的表示，
  避免仅因输入顺序不同而产生不同标识。
- **超出覆盖范围时补查。** 已覆盖的数据可在基础快照上直接裁剪；任务需要额外数据时，
  由宿主执行授权查询并重建投影视图。基础数据复用后，任务投影和文件物化仍可能产生开销。

## 4. 基于依赖水位线的增量缓存失效

通过**领域依赖图（Dependency Graph）**和**版本水位线（Version Watermark）**，
宿主可以识别受业务变更影响的域，减少无关数据的重复读取。
这里的增量单位是业务域：重建受影响的域，复用其余域。

### 4.1 领域依赖声明与反向依赖索引

数据契约声明每个业务视图依赖的数据源，并据此生成反向依赖索引（Reverse Dependency Index）。

```text
正向依赖声明
  商品综合视图   ← 商品、规格、库存、多语言翻译
  活动适用视图   ← 商品、促销规则、活动绑定

反向失效传播
  库存写入       → 商品综合视图需刷新
  促销规则写入   → 活动适用视图需刷新
  商品写入       → 两个视图均需刷新
```

### 4.2 版本更新协议与按域刷新

**业务写入与版本标记可靠关联。** 每次数据源变更都应递增对应的 `sourceVersion`。
一种实现方式是将业务写入和版本递增置于同一数据库事务中，保证提交时同时生效。
后台任务、人工操作、批量导入和 Agent 执行都需要覆盖到这条路径，才能依赖版本号判断新鲜度。

**导出时记录依赖水位。** 每个域保存本次导出对应的数据源版本。
宿主准备数据时，将当前源版本与快照水位逐一比较，仅重建缺失或版本落后的业务域。
缓存命中时仍需要权限、就绪状态与版本元数据检查。

### 4.3 增量刷新与快照发布伪代码

以下过程在同一 `dataKey` 的构建协调范围内执行；并发请求的处理见第 5 节。

```python
def ensure_data_snapshot(scope, requested_domains):
    key = compute_data_key(scope)
    previous_snapshot = get_latest_ready_snapshot(key)
    current_source_versions = read_current_source_versions(scope)
    domains_to_rebuild = []

    for domain in requested_domains:
        domain_snapshot = previous_snapshot.domains.get(domain) if previous_snapshot else None
        if domain_snapshot is None or any(
            domain_snapshot.watermarks[source] != current_source_versions[source]
            for source in DEPENDENCIES[domain]
        ):
            domains_to_rebuild.append(domain)

    if not domains_to_rebuild:
        return previous_snapshot

    fresh_domains = export_consistent_domains(scope, domains_to_rebuild)
    next_snapshot = merge_domain_snapshots(previous_snapshot, fresh_domains)
    publish_ready_snapshot(key, next_snapshot)
    return next_snapshot
```

**数据与水位对应。** `export_consistent_domains` 必须返回同一读取视图中的数据与版本。
可以在数据库的一致性读事务中同时读取二者；也可以在满足第 4.2 节原子更新协议的前提下，
比较导出前后的源版本，版本变化则放弃该次导出并重试。

**保留各域的版本来源。** 合并时，未刷新的域保留原水位，新域使用本次导出的水位。
所有文件构建完成后，原子更新指向就绪快照的引用，避免读到部分产物。
按域合并允许各域来自不同时间截面；要求跨域同一时点数据的任务，应在同一个一致性读取视图中导出相关域。

## 5. 快照生命周期触发器与并发控制

### 5.1 生命周期事件与处理动作

| 事件或触发时机 | 宿主处理动作 |
| --- | --- |
| 首次启用 Agent | 预热匹配的代码与基础数据快照，持久化就绪状态 |
| 再次打开面板 | 检查就绪状态与依赖水位，复用有效产物 |
| 启动任务或请求新域 | 核验资源范围、权限与契约版本，补齐缺失域或重建过期域 |
| 业务写入成功 | 按版本更新协议递增标记；从业务服务返回值获取执行结果 |
| Agent 继续处理刚修改的数据 | 刷新受影响的域，在命令之间切换数据版本并保留会话文件 |
| 权限、语言或筛选范围变化 | 重算 `dataKey` 或更新 `taskScope`，切换或重建对应视图 |
| 应用发布或源码策略变化 | 新会话使用匹配的代码版本；数据契约变更时重建相关数据 |
| 相同缓存键的并发构建请求 | 合并构建工作，等待完成后重新检查调用方所需的域 |

并发请求合并（Request Coalescing / Singleflight）可用于避免相同快照被重复构建。
协调键应与缓存复用范围一致；等待方收到结果后仍要检查自己的请求域是否齐全。
进程内 Singleflight 只覆盖该进程，多进程共享缓存时需要跨进程构建协调，防止重复构建和并发发布覆盖。

### 5.2 高频变更与时间敏感规则

**高频写入域。** 库存等频繁变化的数据可能使快照持续失效。
应根据导出耗时、数据量与任务的新鲜度要求选择刷新粒度，必要时使用微批刷新或按需补查。
最终写入由业务服务读取最新状态并维护业务约束：`expectedRevision` 可检测版本冲突，
库存扣减、支付等操作还需要相应的条件更新、事务或锁机制。

**时间敏感规则。** 限时促销、定时生效合同会在没有数据库写入时改变业务含义。
快照需要记录下一次状态变化时间，或由到期事件触发刷新；仅比较写入版本无法覆盖这类变化。
数据有效期与第 2.3 节用于回收历史产物的保留期分别管理。

## 6. 性能收益拆解与可观测性

### 6.1 核心机制的收益与成本

| 工程机制 | 减少的开销 | 引入或保留的成本 |
| --- | --- | --- |
| 共享只读代码快照 | 每会话复制与扫描同版本源码 | 发布打包、节点导入、多版本存储 |
| 按授权范围复用基础快照 | 每轮重复查询完整业务数据 | 权限检查、水位查询、超范围补查 |
| 基于依赖按域刷新 | 无关业务域的重复导出 | 依赖维护、版本更新、快照合并 |
| 本地 SQLite / JSON 查询 | 已导出数据的重复远程查询 | 初始导出、SQLite 构建、本地存储与计算 |
| 入口索引与按需读取 | 一次性加载全部 Schema 和数据 | 模型的目录探索、文件读取与推理 |

### 6.2 准备链路的可观测性

分别记录端到端准备耗时（Snapshot Preparation Latency）及以下阶段的耗时，
并区分缓存命中、缺失、过期和等待其他构建的情况。

| 阶段 | 观测内容 |
| --- | --- |
| `DomainQuery` | 调用领域服务读取业务数据 |
| `TaskProjection` | 按任务范围过滤、裁剪数据 |
| `Serialize` | 序列化 JSON 与元数据 |
| `SQLiteBuild` | 创建本地表、写入数据与构建索引 |
| `Transfer` | 向执行节点传输快照产物 |
| `Mount` | 准备挂载并启动或刷新执行环境 |

各阶段串行执行时，可以用下式拆解端到端延迟：

```text
TotalPrepLatency = DomainQuery + TaskProjection + Serialize + SQLiteBuild
                 + Transfer + Mount + CoordinationAndMetadata
```

`CoordinationAndMetadata` 包含授权检查、版本查询和构建等待等开销。
存在并行阶段时，应以追踪中的关键路径计算端到端延迟，避免重复相加重叠区间。
基础快照命中可以省去完整业务导出，但任务补查、投影、序列化和挂载是否省略，取决于各自产物的复用情况。
